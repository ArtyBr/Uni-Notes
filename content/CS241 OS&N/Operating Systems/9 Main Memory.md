A program must be taken from disk into **memory** to be **executed**

Once in the memory, the process occupies some **addresses** which store
- **Instructions** to run the process
- **Data** (Input and Output)

The OS must **allocate** a **unique set** of **addresses** to **each process**
- If not, then one process can **modify** data/instructions belonging to **other** processes

The OS must **guarantee** that a process is **only** able to **access** the addresses belonging to that processN
- **Memory protection**

![[Pasted image 20231224135446.png]]
#### Logical vs Physical address space
During the **execution** of a process, the CPU needs to access different addresses belonging to the process
- **Logical (Virtual) address**
	- Generated by the CPU to **fetch** instructions or **read/write** data
	- May be **different** from actual physical address
- **Physical address**
	- Address **seen** by the memory unit
	- A logical address must be **converted** to a physical address before a memory access
- **MMU** (Memory management unit)
	- Special hardware required to **translate** logical addresses to physical addresses

![[Pasted image 20231224135510.png]]
## Memory allocation
Memory allocation deals with how the OS allocated memory to processes and protects that memory from other processes
### Contiguous memory allocation
Each process is contained in a **single** section of memory starting from a **base address**
- Each process occupies a **contiguous** block of addresses

![[Pasted image 20231224135704.png]]

- To **implement** this scheme, the OS needs to decide the **base address** and the **range of addresses** for each process
- **MMU** consists of **relocation** and **limit** registers storing the base address and the range of addresses of a process

![[Pasted image 20231224140006.png]]

- When a process is **scheduled**, the base and limit registers are **loaded** with the corresponding values by the OS
- The **logical address**  generated by the CPU is simply the **offset** from the base address
#### Fixed sized partitions
Memory is **divided** into **fixed size** partitions
- Each partition is allocated to **one** process
- When a process **terminates** the partition is **freed**

**Drawback**: The number of partitions in the memory **fixes** the number of **concurrent** processes in the memory
#### Variable sized partitions
Any available block of memory is called a **hole**
- **Holes** are scattered throughout the memory
- The OS **keeps track** of holes

![[Pasted image 20231224140245.png]]

- When a process **arrives**, it is **allocated** memory from a hole **large enough** to accommodate it
- Process **exiting** **creates** a hole
	- **Adjacent** holes are combined in a **single** hole
#### Dynamic storage allocation problem
OS keeps track of holes and allocate holes to incoming processes
- **First-fit**
	- Allocate the **first hole** that is **big enough**
- **Best-fit**
	- Allocate the **smallest hole** that is **big enough**
	- Must **search** entire list, unless ordered by size
		- Produces the **smallest** leftover hole
- **Worst-fit**
	- Allocate the **largest** hole
	- Must also **search** the entire list
		- Produces the **largest** leftover hole
## Fragmentation
Memory allocation method can **fragment** the usable memory space
- **External Fragmentation** 
	- Total memory space exists to **satisfy a request**, but it is **not contiguous**
		- **Variable partitioning method** suffers from this problem
		- Keeping track of a large number small holes may have a **high overhead**
		- Using **fixed sized** partitions may seem **better** in this respect
- **Internal Fragmentation** 
	- Allocated partition may be much **larger** than **requested memory**
	- This size difference is memory internal to a partition, but not being used
#### Dealing with Fragmentation
- **Compaction**
	- Shuffle memory contents to place all free memory **together** in one contiguous block
		- This approach may have significant **overhead**
- **Non-contiguous memory allocation**
	- Allowing a process to be **scattered** throughout the memory
### Segmentation
Program is divided into **segments**
- Each segment is stored in a **contiguous memory block**
- Each logical address consists of a **two tuple**
	- <segment-number, offset>
- **Segment number** can be mapped to the **base address** of the segment in the memory
- **Offset** is added to it to produce the complete physical address

![[Pasted image 20231226130036.png]]

##### Segment table
- **Indexed** by **segment numbers**
- Each table entry has:
	- **Segment-base**
		- Contains the **starting** physical address where the segments reside in memory
	- **Segment-limit**
		- Specifies the **length** of the segment

![[Pasted image 20231226130947.png]]
### Paging
Segmentation cannot avoid **external fragmentation**
- We can avoid it with **paging**

- Divide **program** into **fixed-size** blocks called **pages**
- Divide **physical memory** into **fixed-size** blocks called **frames**
- **Page size = Frame size** (typically 4KB)
- **Assign** pages to frames
#### Paging model
The **mapping** between page numbers and frame numbers is stored in a **page table**
- For each **process** the OS maintains a **separate** page table

![[Pasted image 20231227033852.png]]
#### Local addresses under paging
Addresses generated by CPU divided into:
- **Page number (p)**
	- Used as an **index** into a page table which contains **base address** of each page in physical memory
- **Page offset (d)**
	- **Combined** with **base address** to define the physical memory address that is sent to the memory unit
- If logical address is $m$ bits and page size is $2^n$ bytes then the **last** $n$ bits is used to denote the page offset
#### Paging hardware and implementation

![[Pasted image 20231226131247.png]]

- Access the page table **directly** from the **memory**
- Need to **store** the **base address** of a page table in the PCB
- When a process is **scheduled** the **base address** of the **page table** is loaded into a register called the **page table base register (PTBR)**
	- Page number is added to the base address to find the location in memory where the corresponding frame number is stored
- **Drawback:**
	- At least **two** memory accesses are required to fetch every instruction/piece of data
		- Each **logical** address to **physical** address **translation** requires a memory access

![[Pasted image 20231227034406.png]]
#### Translation Lookaside Buffer (TLB)
The **TLB** is a hardware **cache** to store **frequently used page table entries**
- Stores a small number of entries: < 256
When the CPU generates a **logical address** its page number is **checked** against all the entries in the TLB in **parallel** to find a **match**
- A TLB search is extremely **fast** - takes **less** than a CPU cycle
Upon **cache miss**, two memory accesses are required
- The missed entry is brought in to the TLB by **evicting** an existing one

#### Paging hardware with TLB
The TLB can store page table entries of **multiple processes**
- In that case, each entry of the TLB requires an **address space identifier (ASID)** to uniquely **identify** the process requesting the TLB search
- If ASIDs **match**, then the frame number is returned
- Otherwise the request is considered to be a **cache miss**
	- Guarantees **memory protection**
#### Smaller page tables
- It is beneficial to use **small page tables**
	- Reduces **memory overhead**
	- Reduce the **page search time** in case of TLB miss
- Modern systems use 32 or 64 bit logical addresses

![[Pasted image 20231227035307.png]]
### Structure of the page table
Most processes only use a **small number** of pages out of the total $2^{20}$ possible pages
- A **valid-invalid bit** is used for each page table entry to **indicate** if there is a physical memory frame **corresponding** to a page number 
	- This bit is 1 when there is **no** physical frame corresponding to a page 
- **Most** of the $2^{20}$ entries of a page table would be **invalid**, yet they would **occupy** valuable memory space 
- It would be **better** if we could group together **several** such **invalid** entries into **one** entry
	- This would **save memory**

![[Pasted image 20231227035750.png]]
#### Hierarchical/Multi-level paging tables
- We **divide** the page table into pages and store **each** page in a **frame** in the memory
- The mapping is stored in an **outer page table**
- If the outer page table is **bigger** than one frame, we can **further divide** it into pages
- The OS does not need to **store** the inner PTs not in use

![[Pasted image 20231227035910.png]]

![[Pasted image 20231227035924.png]]
##### Addressing under multi-level paging
- Outer page table and inner page tables will have $2^{20}$ entries **each**
- 10 bits can be used to index into the **outer** page table
- **Next** 10 bits can be used to index into the **inner** page table 
- 3 memory accesses are required **instead** of 2 
- **Conclusion**: 
	- Multi-level paging **reduces** the **memory overhead** but increases the **number** of **memory accesses** required to read/write data in case of a **TLB miss**

![[Pasted image 20231227040137.png]]
#### Hashed page tables
- **Page numbers** serve as **hash keys** and are hashed to an index of the PT 
- Each entry is **pointer** to a **linked list** of page numbers having the same hash value 
- Each node contains
	- (1) the **page number** 
	- (2) the **frame number**, and 
	- (3) a **pointer** to the **next node**
- Page numbers are **compared** in this chain searching for a **match**
- If a match is **found**, the corresponding **physical frame** is **extracted**

![[Pasted image 20231227040326.png]]
#### Inverted page table
- PowerPC, Itanium use inverted page tables where each **index** **corresponds** to a **physical frame number** 
- Each entry consists of a **pid** and a **page number** 
- When a virtual address is generated, each entry is **searched** until the frame containing the page number and pid is **found** 
- **Decreases** memory needed to store each page table, but **increases** time needed to search the table when a page reference occurs

### Internal fragmentation
- Given a **page size** of 2048 bytes and a **process size** of 72,766 bytes
- We require 35 **frames** plus 1086 bytes
- So we need to allocate 36 frames, which wastes 962 (2048-1086) bytes
### Fragmentation analysis
What is the **worst case** wastage?
- A **single byte** in a frame would result in almost a whole frame being **lost**
So are **smaller frames** desirable?
- Smaller frames mean **larger page tables**
- Page size has **grown** over time (with growing data sets and main memory)
- Solaris uses both 8KB and 4MB pages depending on the data stored
