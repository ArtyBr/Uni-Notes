## a
Another appropriate pattern would be the **Layered** architecture pattern. 
- This would allow each section/layer needed to be implemented in such a way that it sits directly above or below the other layers, only using the services of the layer below it and providing service to the layer above. Rather than the user accessing all data from one place, which with a repository architecture presents one point of failure - disastrous for the service if the data store somehow goes down - the layered structure would just have the data in it's own layer with all other services accessing separate layers as a middleman to it. 
- The UI (Top layer) would just need to access the tracks that have been searched for or recommended for the user, and this layer in turn would have to access a layer below which can store the library of tracks and samples. 
- This makes the app more lightweight in comparison to the repository structure as well, since data transfers only need to go to the overall data store when the layer above needs that information. However in a repository there can be a bottleneck on the data store due to every single component of the app accessing the same data store every time they need access to some data.
- Additionally, it would be easy to develop new features for the app such as adding video playback as a new layer can be created for this rather than re-designing the repository structure from the ground up.
## b
An appropriate software design pattern would be the **Prototype** creational pattern.
- A prototype adds a 'clone' method to the desired object, which creates an exact copy of the object's instance.
- In the app, this can be implemented easily by cloning the sample that the user wants to 'remix', and then allowing them to edit the newly cloned sample - keeping the original intact while being able to interact with a sample that originally is exactly the same as the original.
## c
A good architectural pattern for this would be **Pipe and Filter**.
- This pattern takes an input and purely converts it into some output with an algorithm. Since there isn't anything required on the user end for this process other than just starting the process itself, pipe and filter works great and has minimal overhead in comparison to the other architectural patterns.

The **Decorator** pattern would be useful for the production of different types of track.
- Since the different algorithms use various shared features, the decorator pattern would allow the developers to create classes for each of the necessary features, which can then be implemented in each algorithm as needed. This would minimize unnecessary code since the shared features do not have to be duplicated for each algorithm in order to use them.

## a
**User-acceptance**:
- Bring in a collection of the target users, which in this case seems could probably include people on the street who are interested in mobile apps. Get them to try to import audio files, without telling them how to do it exactly. Get feedback from them saying how easy or difficult they found the action, or if any errors occurred. At the end, ask the users if they deem the function acceptable for release.
**White-box**:
- Since there are multiple stages/conditions during the function process, create a test to see what the system should do in each stage. For example once the user selects the import option and a list of possible sounds comes up, what happens if they click 'back'? What happens if they click a sound? After this, what happens if they click away from the sound instead of on it a second time? etc.
**Black-box**:
- When import button clicked, check which sounds retrieved from database. Check this for multiple configurations of sounds in the database, and have a valid set of results to check against.

## c
Since the issue at hand affects the hardware of the device, one way of making the system more dependable would be to use **protection systems**.
- In the given case, since the issue is affecting the heat of the phone due to unwanted resource requests, there could be some sort of counter which is given some standard or maximal request count, and if this is exceeded it could stop these requests, or in the worst case it could forcefully shut the app down.
- Additionally, this wouldn't be a particularly difficult issue to fix in this way, and so by doing it quickly like this it would prevent actual damage of property, which is more important in the short run than trying to come up with some actual solution to the cause of the issue.
## d
**N-version programming** is a dependability architecture in which multiple separate development teams create some '$n$' number of software units, and the results of these units are compared to each other - with the overall software choosing the output occurring from the majority of these units.
- This could be used to fix the resource request issue, as the software can run in parallel with these different versions calculating what it should do at each user action, and if one of the versions happens to make a spontaneous, unnecessary resource request, the others wouldn't, and so the issue would be avoided.
- This relies on the fact that the development teams are diverse in their programming techniques in order to make sure that the versions aren't too similar to each other, causing the same bug.
- Another disadvantage is that running multiple copies of the same software at the same time will decrease performance and so the app may run slower than if it was just running from one instance.
