# 3
## a
The Piper and Filter architectural pattern described a pattern where inputs are provided to the system and are processed, producing an output in the other way. This method is useful for systems that require lots repeated tasks with minimal user input. Because of this, Pipe and Filter would **not** be a good architectural pattern for this application - since a conference room is not an object which will return some output constantly based on inputs into it.

The MVC architectural pattern uses a Model, a View and a Controller to manipulate inputs from a user and affect the system in which they operate. It is great for systems with a GUI since when a user makes a change in the GUI, the controller processes it and affects the Model, which stores the data and other information for the system. It also allows for multiple different views to be made regardless of the model and controller, which makes it **ideal** for the 'Conference Room' system, as a different room can correspond to a different view and controller. 
## b
The **decorator** design pattern would be best for this as it creates extra classes which can add on features to objects irrespective of previous features that were already added on. This would mean that there can be one class created for each new desired feature rather than having to make classes for every combination of desired features. Additionally, it can be easily extended for each new feature, so it would be the best fit for this usecase.
## c
A good architectural pattern to use would be the **repository** pattern. All hash codes can be stored in one central repository, and each action requiring a hash code can access this. Considering the fact that it's unlikely that many of such requests will be made in quick succession, the downside of a repository of bandwidth limitation in terms of lots of transfers from one store will not be a problem. Additionally, since this isn't exactly a core feature, if the repository goes down, as it has one point of failure, it won't shut down the entire system.

The software design pattern for this would be the **strategy** behavioural pattern, since it separates each algorithm from the overall object (the media being sent) and makes a specific instance for each algorithm that we want to incorporate into each different object that has a different hashing algorithm for it.
## d
The first suggestion doesn't adhere to the Open/Closed principle, which requires that after a class has been completed, it is open for extension, but not for modification. Since the first person suggests to modify the class for each client, it does not adhere to this principle.
The second person suggests having sub-classes with different permissions enabled or disabled. This promotes the Liskov substitution principle, as each of the subclasses can be replaced by the parent class and still have the intended function, except they have different permissions enabled. It would also follow the interface segregation principle as each class doesn't depend on methods it doesn't use.
